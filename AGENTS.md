# Руководство по работе с репозиторием

## Структура проекта и организация модулей

Репозиторий содержит минимальное приложение на React и TypeScript со сборкой через Vite.

- `src/main.tsx` — точка входа, инициализирующая React.
- `src/app/` — сборка приложения и глобальные стили в папке `styles/`.
- `src/pages/` — папки страниц, например `home/`, с компонентами, SCSS-модулями и явными экспортами в `index.ts`.
- `public/` — статические ресурсы, доступные напрямую; `dist/` — результат сборки.
- Конфигурационные файлы в корне задают настройки Vite, TypeScript, ESLint, Prettier и Stylelint.

Для импортов из `src/` используйте алиас `@/`, например `import { HomePage } from "@/pages/home"`.

## Команды разработки, сборки и проверки

Установите зависимости командой `npm install`, затем используйте:

- `npm run dev` — запуск сервера разработки на порту 5173.
- `npm run build` — проверка TypeScript и создание продакшен-сборки в `dist/`.
- `npm run preview` — локальный просмотр продакшен-сборки.
- `npm run typecheck` — проверка TypeScript без генерации файлов приложения.
- `npm run lint` и `npm run lint:style` — проверка TypeScript/React и CSS/SCSS соответственно.
- `npm run format:check` — проверка форматирования через Prettier.
- `npm run lint:fix`, `npm run lint:style:fix` и `npm run format` — автоматические исправления; проверяйте получившиеся изменения.

## Стиль кода и правила именования

Используйте отступы в два пробела, двойные кавычки, точки с запятой и ширину строки Prettier в 100 символов. Сохраняйте строгий режим TypeScript и предпочитайте именованные экспорты функциональных компонентов.

Называйте компоненты и их файлы в PascalCase (`HomePage.tsx`), папки страниц — в kebab-case (`user-profile/`), хуки — в camelCase с префиксом `use`. Размещайте `ComponentName.module.scss` рядом с компонентом; используйте `.root` для корневого элемента и классы по назначению, например `.title`. Глобальные стили храните в `src/app/styles/`.

Соблюдайте группировку и алфавитную сортировку импортов, заданные ESLint. Разделяйте группы пустыми строками. В `index.ts` перечисляйте экспорты явно.

## Проверка изменений

Тестовый фреймворк, команда запуска тестов, требования к покрытию и правила именования тестов не настроены. Перед отправкой изменений выполните проверку типов, оба линтера, проверку форматирования и продакшен-сборку. Проверьте затронутое поведение интерфейса через сервер разработки и опишите ручные проверки в запросе на слияние.

## Коммиты и запросы на слияние

В последних коммитах используются префиксы Conventional Commits: `chore(deps):`, `refactor:`, `docs:`, часто с описаниями на русском. Следуйте этому формату: кратко указывайте выполненное действие.

Ограничивайте запрос на слияние одной задачей. Объясняйте суть и цель изменений, добавляйте ссылки на связанные задачи, перечисляйте выполненные проверки и прикладывайте скриншоты при изменении интерфейса. Избегайте несвязанного рефакторинга и включения результатов сборки.
